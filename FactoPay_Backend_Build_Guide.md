# FactoPay Backend Build Guide
### For Christian (Lead Backend Developer) and the Backend Team
### Stack: TypeScript end-to-end (NestJS) · 14-Day MVP Sprint

---

## Part 1 — What "The Backend" Actually Means Here

Before assigning a single task, the team needs to internalize this: **the backend is not "the API." It is the financial system.** The Flutter app is a window into it. The blockchain is a settlement rail underneath it. Compliance evidence is generated by it. If the backend is sloppy, nothing else matters — a beautiful app on top of a broken ledger is just a faster way to lose money.

Everything below is organized so that four backend engineers (you + 3 devs) can work in parallel for 14 days without stepping on each other, while still producing one coherent, reviewable system.

**Ground rules that apply to every line of backend code:**
1. TypeScript strict mode, everywhere. No `any` in domain or application layers.
2. Money is never a `number`/`float`. Use fixed-precision decimals (Postgres `DECIMAL(18,4)` / a decimal library like `decimal.js` in code — never native JS floats for financial math).
3. All timestamps stored and compared in UTC.
4. No direct wallet balance writes — balances are always derived from ledger entries.
5. Every state-changing endpoint that touches money requires an `Idempotency-Key`.
6. Nothing gets merged without a peer review, and the PR author must be able to explain every line, including AI-assisted lines.

## Part 2 — The TypeScript Backend Stack

| Layer | Technology | Why |
|---|---|---|
| Language | TypeScript (strict) | Type safety across the whole domain, shared types with frontend if needed |
| Framework | NestJS (Node.js) | Modular, DI-based, maps cleanly to DDD bounded contexts, enterprise-grade |
| ORM | Prisma or TypeORM | Migrations, type-safe queries. Prisma recommended for MVP speed |
| Primary DB | PostgreSQL | ACID compliance — non-negotiable for a ledger |
| Cache/Sessions | Redis | Idempotency key checks, FX quote expiry (30s), rate limiting |
| Validation | class-validator + class-transformer (or Zod) | DTO validation at every API boundary |
| Auth | Passport.js + JWT (jsonwebtoken) | Access/refresh token strategy |
| Blockchain SDK | `stellar-sdk` (Node) | Stellar testnet integration |
| Testing | Jest + Supertest | Unit + integration tests |
| API Docs | `@nestjs/swagger` | Auto-generates OpenAPI spec from your DTOs/decorators |
| Queue (optional but recommended) | BullMQ (Redis-backed) | Webhook retries, dead-letter queue |

Everything — API, background jobs, webhook handlers, blockchain adapters — is TypeScript. No mixing languages. This keeps the whole team able to read and review each other's code.

### Backend Developer 2 — Auth & Compliance
**Owns:** `auth-identity` and `kyc-management` bounded contexts.

What they build:

- The **KYC state machine**: `UNVERIFIED → PENDING → UNDER_REVIEW → APPROVED / REJECTED`, implemented as an explicit state field with guarded transitions (reject illegal transitions at the domain layer, not just the UI).
- `SubmitKycUseCase`, `ReviewKycUseCase`, `ApproveKycUseCase` — for the MVP, KYC is simulated (mock Sumsub responses), but the state machine and events must behave exactly as they would in production.
- The `KycApprovedEvent` — this is the critical hand-off to Dev 1's wallet provisioning. Get this contract agreed with Dev 1 on Day 3, in writing, before either of you build it.
- The **audit-compliance** context: `WriteAuditTrailUseCase`, and the global `AuditLogInterceptor` that captures every state-modifying request across the whole app (who did what, when, before/after state) into an immutable `audit_logs` table.
- `AuthController` and `KycController`.

### Backend Developer 3 — Blockchain, FX & Webhooks
**Owns:** `blockchain-settlement`, `transfer-engine` (FX side), and `gateway-integrations`.

What they build:
- `IStellarGateway` interface + `StellarService` implementation wrapping `stellar-sdk`, targeting **testnet only** for the MVP. Never handle real private keys — testnet keypairs live in environment variables, never logged, never committed.
- `SubmitToStellarTestnetUseCase`, `UpdateStellarTxHashUseCase`.
- `FxQuote` value object with **30-second expiry logic** — `RequestQuoteUseCase` locks a rate for exactly 30 seconds; anything after that must be re-quoted.
- `InitiateTransferUseCase` — orchestrates the whole transfer: checks KYC status, checks wallet balance, locks FX quote, calls Dev 1's `PostLedgerTransactionUseCase`, calls the Stellar service, and updates transfer state at every step.
- `WebhookSignatureValidator` — HMAC verification for simulated Flutterwave/Transak webhooks. Any unsigned or forged webhook is rejected and logged, never silently accepted.
- Webhook retry/dead-letter logic (1 min → 5 min → 15 min → 1 hour → DLQ after 5 failures), ideally via BullMQ.
- `TransferController`, `RatesController`, `WebhookController`.

### How the four of you avoid collisions
- Dev 1 and Dev 3 both touch `transfer-engine` — Dev 3 owns orchestration/state transitions, Dev 1 owns anything that actually posts to the ledger. The rule: **Dev 3's code calls Dev 1's use case; Dev 3 never writes ledger entries directly.**
- Dev 2's `KycApprovedEvent` and Dev 1's wallet listener are the other seam — agree on the event payload shape by Day 3 (event name, `userId`, timestamp, KYC tier) so you're not blocked on each other.
- You (Christian) own the `shared/` kernel so nobody duplicates exception classes, value objects, or the idempotency middleware.

## Part 8 — Implementing the Core Guardrails (How-To, Not Just What)

These four things are what separate "an app that moves numbers around" from "a financial system." Every dev needs to understand *why*, not just copy a pattern.

### 1. Transaction Locking (prevents double-spend)
Every operation that reads a balance and then writes based on it must happen inside a single database transaction with `SELECT ... FOR UPDATE` on the relevant wallet row. If two requests hit "send money" from the same wallet simultaneously, the second one must wait for the first to fully commit or roll back — never read a stale balance. In Prisma/TypeORM this means wrapping the read-check-write sequence in `$transaction`/`queryRunner.startTransaction()`, with the row lock as the first statement inside it.

### 2. Idempotency (prevents duplicate charges)
Client sends `Idempotency-Key` header on every transfer-initiating request. Middleware (owned by Christian, in `shared/infrastructure/idempotency/`) checks Postgres/Redis for that key before the request reaches the controller. If it exists, return the stored response immediately — do not re-run the use case. If not, proceed, and store the key linked to the resulting `transfer_id` once the operation completes. This is what makes a frontend retry (e.g., after a network blip) safe instead of dangerous.

### 3. Webhook Integrity (prevents fake "payment successful" fraud)
Every inbound webhook (`/webhook/flutterwave`, `/webhook/transak`) must have its HMAC signature verified against a shared secret **before** any business logic runs. An unsigned or mismatched signature gets rejected and logged — full stop, no partial processing. Retries follow 1 min → 5 min → 15 min → 1 hour, and after 5 failures the event goes to a dead-letter queue for manual investigation. Never mark a payout `COMPLETED` on an unverified webhook.

### 4. The Ledger Rules (prevents money from silently vanishing or duplicating)
- Every transaction produces at least one debit and one credit; they must sum to zero.
- Nobody ever runs `UPDATE ledger_entries` or `DELETE FROM ledger_entries` — reversals are new entries, not edits.
- Wallet balance is *always* `SUM(credits) - SUM(debits)` computed on read (or a maintained read-model that's rebuilt from entries), never a column that gets directly incremented/decremented.

**Worked example your team should implement as a test case (from your own docs):** a €200 transfer with a 1% FX spread produces exactly these entries — `USER_WALLET(EUR) -200 / SETTLEMENT_ACCOUNT(EUR) +200` → `SETTLEMENT_ACCOUNT(EUR) -2 / FEE_ACCOUNT(EUR) +2` → `SETTLEMENT_ACCOUNT(USDC) +198 / RESERVE_ACCOUNT(USDC equiv) -198` → `RESERVE_ACCOUNT(USDC) -198 / PAYOUT_ACCOUNT(GHS float) +equiv`. If Dev 1's `DoubleEntryEngine` can't produce and validate this exact sequence, it isn't done.

## Part 9 — State Machines (Implementation Notes)

**KYC** (`UNVERIFIED → PENDING → UNDER_REVIEW → APPROVED / REJECTED`): implement transitions as an explicit method on the domain model (e.g., `kycRecord.approve()`) that throws if called from an illegal state — never let a controller or service set the status field directly.

**Transfer** (`CREATED → PENDING_KYC → COMPLIANCE_REVIEW → FX_LOCKED → WALLET_DEBITED → BLOCKCHAIN_CONFIRMED → PAYOUT_PENDING → COMPLETED`, with `FAILED` reachable from most states): same rule — transitions are domain methods, not raw field assignments. Log every transition to `transfer_events` so the full history is reconstructable for compliance and debugging.

**The single most important operational rule for both machines:** when something goes wrong, prefer `FAILED` over uncertainty. Never mark a transfer `COMPLETED` speculatively. Always log before retrying. Never silently "fix" a stuck transfer in the database — that becomes a support runbook step, not a code path.

## Part 12 — Definition of Done & PR Discipline

A backend PR is not done until:
1. It includes tests, and they pass locally.
2. It's reviewed by at least one peer who can explain why the change is correct — no rubber-stamp approvals, especially on `wallet-ledger` or `transfer-engine` where Christian reviews personally.
3. Any AI-assisted code has been read, understood, and can be explained by the author (per your AI usage policy — AI drafts, humans own).
4. It doesn't touch another dev's bounded context directly — cross-context calls go through the owning module's public use-case, never through a reached-in repository or entity.
5. Relevant `.md` docs are updated in the same PR, not "later."

## Part 13 — The Backend's Role in the Day-14 Demo

Everything above exists to make this sequence work flawlessly, end to end, live:

1. Register + login (Dev 2's auth) → JWT issued.
2. Submit mock KYC → admin approves → `KycApprovedEvent` fires → wallet auto-provisions (Dev 2 → Dev 1 handoff).
3. Request FX quote, locked 30s (Dev 3).
4. Initiate transfer with `Idempotency-Key` (Dev 3 orchestrates, Dev 1 posts ledger entries).
5. Simulated Stellar transaction hash returned (Dev 3).
6. Compliance record + immutable audit log generated automatically (Dev 2's interceptor).
7. Admin dashboard shows the completed transfer, the FX spread sitting in `FEE_ACCOUNT`, and the simulated float deduction (Christian/Dev 2, pulling from Dev 1's ledger).

If any one of those seven steps breaks, it's almost always because one of the two integration checkpoints (Day 5–6 KYC→Wallet event, Day 7–9 Transfer→Ledger call) wasn't tested together early enough — which is why those checkpoints are marked explicitly in the build order above rather than left until the end.

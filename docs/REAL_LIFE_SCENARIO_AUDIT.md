# FactoPay Real-Life Scenario Audit

Date: 2026-07-16

This audit describes what the current backend can handle today, what happens in realistic failure or abuse scenarios, and what should be added before production. It is based on the current `dev` branch implementation after the security/session/webhook hardening batch.

## Executive Verdict

The project can now handle core authenticated transfers, wallet debits, ledger reversals on settlement failure, KYC-gated limits, refresh-token rotation, raw-body webhook signature checks, B2B API-key transfers behind a feature flag, and rewards crediting after completed transfers.

It is not production-complete for account deletion, user logout/session management endpoints, provider webhook replay protection, transfer cancellation, formal dispute handling, full ledger immutability enforcement at the database layer, health/readiness checks, and operational reconciliation jobs.

## Scenario Matrix

| Scenario | What The System Does Today | Production Recommendation |
|---|---|---|
| User wants to delete their account | There is no self-service delete endpoint. Admins can suspend users, which sets `isActive=false` and revokes active auth sessions. A hard database delete would be risky because financial records, transfers, wallets, ledger entries, blockchain records, KYC, audit logs, and rewards have retention and reconciliation requirements. | Build an account-closure workflow, not a raw delete. Add `AccountClosureRequest`, set user status to `CLOSURE_REQUESTED` or `CLOSED`, revoke sessions, API keys, and MFA secrets, block new transfers, anonymize PII after legal retention, preserve immutable ledger/audit/transfer records, delete or archive KYC documents according to compliance policy, and notify the user. |
| User loses network after tapping send | If the request reached the server, the transfer may continue even if the client never receives the response. The transfer endpoint requires `Idempotency-Key`; a retry with the same key either gets a `409` while the first request is still processing or the cached successful response after completion. | Client must generate one idempotency key per transfer intent and reuse it on retry. Add `GET /transfers/:id` or `GET /transfers/by-idempotency-key/:key` so the app can recover after network loss. Add user-facing statuses: `CREATED`, `WALLET_DEBITED`, `BLOCKCHAIN_PENDING`, `COMPLETED`, `FAILED`. |
| User keeps tapping the send/pay button | If the frontend reuses the same `Idempotency-Key`, Redis locks the first request for 120 seconds, concurrent taps return conflict, and the successful response is cached. If the frontend creates a new key for each tap, the backend treats each as a separate transfer attempt. | Keep the backend idempotency rule and enforce frontend behavior: disable the button after first tap, reuse one key per payment intent, and show progress. Add a database `paymentIntentId` or unique client reference per user/recipient/amount/quote to protect against bad clients generating new keys. |
| B2B partner retries a transfer | B2B transfer endpoint now requires an `Idempotency-Key`; it no longer generates a fallback key. API keys are validated, revoked keys are rejected, and dynamic rate limits are tested. The B2B module is feature-flagged off by default. | Keep B2B disabled until partner onboarding and runbooks are ready. Add partner-level transfer status lookup, webhook delivery retries, API key rotation, dashboard audit logs, and per-partner limits. |
| FX quote expires before transfer | Transfer orchestration reads the quote from Redis. If it is missing or expired, the use case throws `FxQuoteExpiredException`. | Frontend should refresh the quote and ask the user to confirm the new rate. Add a quote status endpoint and avoid showing stale rates after TTL. |
| User has insufficient wallet balance | Ledger posting locks affected wallets/accounts and checks balance before debit. Insufficient balance rejects the posting and marks the transfer failed if the transfer record was already created. | Add preflight balance checks for better UX, but keep the atomic ledger check as the source of truth. Return clear error codes and do not rely on client-side balance only. |
| User is not KYC-approved | Transfer orchestration checks `user.kycStatus`. Non-approved users are blocked. Monthly limits are enforced by KYC tier. | Keep this. Add a user-facing remediation flow that explains the required KYC action and remaining monthly limit. Consider a dedicated `GET /limits/me` endpoint. |
| User crosses monthly KYC transfer limit | The transfer use case sums completed monthly transfers and rejects transfers above tier limit. | Keep the check, but make it transaction-safe for high concurrency by calculating/reserving limits inside a serialized transaction or a dedicated limit ledger. Add admin override audit trail. |
| Recipient does not have a provisioned Stellar wallet | Transfer engine reverses ledger entries, marks transfer `FAILED`, emits `transfer.failed`, and throws an error. | Validate recipient payout readiness before wallet debit. Provision wallet on KYC approval and add a pre-transfer recipient eligibility check. |
| Blockchain settlement succeeds | The blockchain use case records the transaction, updates it to `SUCCESS`, transfer status becomes `COMPLETED`, and `transfer.completed` is emitted. Rewards and notifications can react to that event. | Keep. Add reconciliation jobs that verify blockchain success independently and alert if internal status and chain status diverge. |
| Blockchain settlement fails after ledger debit | Transfer engine reverses the ledger transaction, marks transfer `FAILED`, emits `transfer.failed`, and tests verify sender balance is restored. | Keep. Add customer notification, admin review queue, and failure reason taxonomy. Ensure reversal entries are immutable and easy to audit. |
| Blockchain timeout or uncertain chain state | Settlement use case tries verification. If inconclusive, blockchain transaction can become `PENDING_VERIFICATION`; transfer engine maps non-success to `BLOCKCHAIN_PENDING`. | Add a scheduled reconciliation worker that re-verifies pending transactions until final state, with alerts after SLA breach. Add user-facing "processing" copy, not "failed", for this state. |
| Wrong recipient or wrong destination address | Destination allowlist exists for settlement destinations. Once on-chain settlement succeeds, funds are not practically reversible. | Add recipient confirmation screens, saved beneficiary verification, cooling-off/risk checks for new beneficiaries, and transaction review for high-risk destinations. |
| Provider sends duplicate webhooks | Flutterwave webhook is signed and queued. Transak signature is checked and event emitted. Sumsub signature is checked and user KYC is updated by external applicant ID. There is no complete provider event-id replay table yet. | Add `webhook_events` table with provider, event id, received timestamp, signature timestamp, processing status, and unique constraint. Reject stale timestamps and duplicate event ids. |
| Provider sends tampered webhook body | Raw request body is preserved globally and HMAC checks use raw bytes plus timing-safe comparison. Invalid signatures are rejected. | Keep. Never log expected or received signatures. Add replay protection and provider timestamp tolerance. |
| Provider webhook arrives out of order | Current handlers do not fully model provider event ordering. Some updates may be idempotent, but there is no formal state machine guard for all provider events. | Store events first, process with state transition rules, ignore stale transitions, and make every webhook processor idempotent. |
| User password or refresh token is stolen | Refresh tokens are now stored by hash in `auth_sessions`, include `jti`, rotate on use, and reuse of revoked/mismatched token revokes active user sessions. JWT/session fingerprint uses IP subnet and user agent. Access tokens expire in 15 minutes. | Add logout/current-session and logout-all-devices endpoints. Consider access-token denylist only for high-risk events. Notify users on suspicious refresh-token reuse. |
| User logs out | There is no explicit logout endpoint. Client can discard tokens, but server-side session revocation only happens through refresh rotation/reuse detection or admin suspension. | Add `POST /auth/logout` to revoke current `authSession` by refresh token or `jti`, and `POST /auth/logout-all` to revoke all sessions. |
| Admin suspends compromised user | Admin endpoint exists. It prevents self-suspension, sets `isActive=false`, revokes sessions, and logs an admin audit event. JWT strategy rejects inactive users. | Keep. Add reason codes, user notification, support ticket linkage, and forced review before unsuspension. |
| User changes phone/email | Profile update exists. Phone numbers are encrypted and blind-indexed. | Require OTP re-verification for phone/email changes, revoke high-risk sessions after sensitive profile changes, and keep previous-contact audit history. |
| User loses MFA device | MFA setup/enable/disable and backup code support exist. Disable requires current TOTP or backup code. | Add support-assisted MFA reset with KYC/admin approval, cooldown periods, and audit trail. |
| User requests KYC resubmission or is rejected | Admin KYC approve/reject/request-resubmission/upgrade flows exist. Sumsub webhook can update KYC status. | Add user-facing resubmission endpoint and document lifecycle policy. Add event history visible to support. |
| Fraud or AML risk is detected | AML/audit modules exist and tests cover alerts. Transfer flow emits events that can feed monitoring. | Add real-time fraud rules before wallet debit, review holds, blocked beneficiary lists, velocity checks, and manual release workflow. |
| Redis is down | Redis backs idempotency, FX quotes, locks, and queues. Some tests mock it. In production, transfers that need Redis should fail closed rather than proceed unsafely. | Add readiness checks for Redis and queues. Make idempotency and quote checks fail closed with clear `SERVICE_UNAVAILABLE`. Add Redis HA and alerts. |
| Database is down or slow | Prisma errors bubble up. Some tests show real DB latency. No dedicated health/readiness endpoint exists yet. | Add `/health/live` and `/health/ready` for DB, Redis, queues, and Stellar. Add connection pool metrics, slow-query alerts, and DB failover runbooks. |
| User transfer is stuck in `BLOCKCHAIN_PENDING` | Current system can represent pending chain verification, but there is no visible reconciliation worker in this batch. | Add scheduled reconciliation and admin queue. Customer support should see pending reason, last verification attempt, and next retry time. |
| User wants to cancel a transfer | There is no cancel endpoint. Once wallet debit or blockchain settlement begins, cancellation may not be safe. | Add `POST /transfers/:id/cancel` only for pre-debit states like `CREATED` or `PENDING_KYC`. After debit, use failure/reversal or support workflow only. |
| Ledger entries are edited by mistake or maliciously | Application logic is append-style and reversals create inverse entries. There are no DB triggers yet that block `UPDATE`/`DELETE` on ledger entries. | Add database triggers/rules to prevent update/delete on `ledger_entries`. Add `LedgerTransaction` header table with unique transaction id and immutable entries. |
| Rewards fails after transfer completion | Rewards crediting listens to `transfer.completed`; failures are logged and should not break the completed transfer. | Add outbox pattern or event replay table so rewards can be retried without affecting money movement. |
| Notification provider fails | Adapters fail closed on missing config. Notification failures should not roll back completed transfers. | Add notification retry queue, provider failover, templates, delivery status, and support visibility. |
| API abuse or brute force login | Global throttling is configured. Auth routes have stricter throttle limits. B2B has API key throttling. | Use distributed throttling backed by Redis in production. Add IP/device/email risk scoring, CAPTCHA/challenge after repeated failures, and alerting. |
| Secrets are missing in production | New required env validation fails startup when core secrets are missing. Production env requires DB, origins, notifications, Stellar, and encryption keys. | Keep fail-fast startup. Add CI secret scanning and credential rotation runbook. Do not load feature flags solely from late secret managers because module imports are decided at app-load time. |
| Swagger/API docs in production | Swagger is disabled by default in production unless `ENABLE_SWAGGER=true`. CSP is enabled globally. | Keep disabled publicly. If enabled, put behind VPN, SSO, or IP allowlist. |

## Priority Gaps To Close Next

1. Account closure and data-retention workflow.
2. Logout and session-management endpoints.
3. Transfer status lookup by transfer id and idempotency key.
4. Webhook replay protection with provider event table and timestamp tolerance.
5. Reconciliation workers for `BLOCKCHAIN_PENDING` and provider webhooks.
6. Ledger immutability at the database level.
7. Health/readiness endpoints for DB, Redis, queues, and Stellar.
8. Client payment-intent model to prevent duplicate sends even when clients generate new idempotency keys.
9. Admin/support dashboard flows for failed, pending, disputed, and cancelled transfers.
10. CI gates for secret scanning, migrations, tests, audit, and lint.
